Tessary watches agents running in production. It reads every trace your agents produce, runs classifiers over all of them to detect changes and likely problems, checks whether each detected change is a real issue, and then investigates what caused the ones that are.

The four stages have names you will see throughout these pages. A classifier creates a **finding** when it detects a change. **Triage** decides whether the finding is a real issue. A validated finding becomes a **case**. An agentic RCA (root-cause analysis) run then investigates the case and reports what it thinks caused it.

You can run Tessary two ways, and these pages cover both. Tessary Cloud is the hosted service. The open edition is the code in the [tessary repository](https://github.com/tessaryai/tessary), released under the [Apache License 2.0](https://github.com/tessaryai/tessary/blob/main/LICENSE), and you self-host it.

## Sign up for Tessary Cloud

Tessary Cloud is the quickest way to start, because there is nothing to deploy. Sign up at [app.tessary.ai](https://app.tessary.ai) and your first project opens on the connect screen. It is free, and a one-time model credit pays for triage and root-cause analysis until it is used up or you add your own model provider key. Limits on traces, stored data, and retention are on the [pricing page](https://tessary.ai/pricing).

[Start on Tessary Cloud](/cloud/quickstart) takes you from sign-up to your first finding.

## Self-host Tessary

Self-host when you want Tessary running on your own infrastructure. A deployment is a single-node Docker Compose stack, and every credential it needs ships with a working default. Paste this into your coding agent:

```text
Self-host Tessary for me by following https://github.com/tessaryai/tessary/blob/main/setup.md
```

[`setup.md`](https://github.com/tessaryai/tessary/blob/main/setup.md) is written as instructions to an agent: install what is missing, bring every service up, verify the frontend, and hand back the URL. It needs Docker Engine 26 or newer and Docker Compose v2.34 or newer on the machine.

Prefer to run it yourself? The same install is one command, with nothing cloned and no `.env` to edit:

```bash
docker compose -f oci://docker.io/tessaryai/tessary:compose up -d -y
```

Either way, open `http://localhost` once `docker compose -p tessary ps` reports every service healthy, and create the first account with an email and password. Three of the shipped credentials are placeholders published in the repository, so this install is a localhost test drive until you replace them. [Secure the instance](/self-hosting/setup#secure-the-instance) covers that, and it is not something the agent does for you.

## What runs where

Five classifiers run out of the box on both: `duration_drift`, `cost_drift`, `tool_error`, `secret_leak`, and `malformed_output`. [`frustration`](/classifiers/frustration) starts switched off on both and needs an OpenRouter or TypeSafe key. [`groundedness`](/classifiers/groundedness) is on from the start on Tessary Cloud; self-hosted, it starts switched off and needs its model running on a Mac with Apple silicon or a GPU instance on AWS.

Triage and root-cause analysis work on both. On Tessary Cloud, the model credit pays for them at first, and you start triage by hand on each finding. Self-hosted, both need a model provider credential you supply, and automatic triage is available but starts switched off, so nothing spends against your provider account until you turn it on.

## Start in three steps

<Steps>
  <Step title="Start Tessary">
    Sign up at [app.tessary.ai](https://app.tessary.ai). To self-host instead, take either self-host path above, create your account, and replace the three placeholder secrets. [Start on Tessary Cloud](/cloud/quickstart) and [Set up Tessary](/self-hosting/setup) cover each path end to end.
  </Step>
  <Step title="Instrument your agent">
    Send traces to the OTLP (OpenTelemetry Protocol) endpoint, and tag every span that covers a model call with a `tessary.call_site.id` attribute. There is no Tessary client library to install, and the connect screen carries a prompt you can hand to a coding agent. [Instrument your agent](/instrument/overview) covers both paths.
  </Step>
  <Step title="Review what Tessary finds">
    Classifiers need a stretch of your own traffic before they can tell a change from normal variation. Once they have it, findings start arriving.
  </Step>
</Steps>

## What you see after connecting traces

The project reports its progress as a milestone ladder, and **Triage** names the stage whenever the queue is empty. A new project reads `not_connected`, then `listening` once the endpoint is live, then `fitting` once traces are arriving. Classifiers stay at `fitting` while they learn what your traffic normally looks like, which takes a while on low volume and is expected rather than a fault.

After that, three things appear in order:

| You see | What it means |
| --- | --- |
| A **finding** on the Classifiers page | A classifier detected a change and recorded the production evidence for it. It is not yet a validated issue. |
| A **case**, once triage validates the finding | Triage reviewed the evidence and decided the change is a real issue worth attention. A high-confidence secret leak and a frustration finding skip triage and open a case as soon as they are filed, because their numbers are the claim. |
| An **RCA report** on the case | The agentic run reports a one-sentence summary, the causes it found with the traces it cites for each, and the checks it ruled out. Connect a repository and it can ground that work in your own code. |

Tessary explains the issue and hands it to you. It does not open the fix.
