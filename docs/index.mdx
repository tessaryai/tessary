Tessary is an open-source agent reliability platform for engineering teams running AI agents in production. It reads every trace your agents produce, flags the ones that moved using classifiers cheap enough to run on all of them, validates the flags that hold into cases, and explains a case with an agentic RCA (root-cause analysis) run, grounded in your own repository when you connect one.

Agents develop production issues without crashing and without failing visibly. Once an agent is mature, most of its failures are low-frequency, which is why watching a sample of traffic structurally cannot find them. Tessary watches all of it, and treats identifying a problem as the beginning of the work rather than the end of it.

These pages document the open edition, the code in this repository, which is open source under the Apache License 2.0. They do not document Tessary Cloud, the hosted service. Parts of the product do not run here at all: [what the open edition leaves out](#what-the-open-edition-leaves-out) names them.

Those three are the order of the work: stand up an instance, point an agent at it, then read what comes back. A new project stays on the connect gate until one span carrying a `tessary.call_site.id` attribute arrives.

## Instrument your agent

Instrumenting means two things: traces reach the OTLP (OpenTelemetry Protocol) endpoint, and every span covering a model call carries a call-site tag. There is no Tessary client library to install.

- [Instrument your agent](/instrument/overview) is the task, either by handing the connect screen's prompt to a coding agent or by wiring the exporter yourself.
- [The call-site tag](/instrument/call-site-tag) covers what a call site is, how to choose an id that survives, and where the attribute goes in code.
- [Configure an exporter](/instrument/exporters) covers the three forms: environment variables, an in-code span processor, or a collector you already run.
- [Span requirements](/instrument/span-requirements) lists every field Tessary reads off a span, with accepted values and constraints.
- [Instrumentation troubleshooting](/instrument/troubleshooting) works through nothing arriving, spans arriving untagged, and a connect gate that stays closed.

## Self-hosting

A deployment is a single-node Docker Compose stack. One command boots it, because every credential the stack needs ships with a working default. Two of those defaults are placeholders published in the repository, and replacing them is part of setup.

## What the open edition leaves out

Four classifiers exist in the product and cannot run here. `frustration` and `groundedness` depend on a separate encoder service that this configuration does not start and whose model weights are not published. `behavior_drift` and `sop_conformance` ship as catalog entries with no detector behind them. The other five classifiers run out of the box. [Classifiers and findings](/concepts/classifiers-and-findings#what-the-open-edition-runs) covers both sides of that line.

Two more boundaries are worth knowing before you evaluate:

- **Automatic triage is off by default**, in every edition, because running it unattended drives model spend with no ceiling. Findings are still filed and still visible; nothing escalates them on its own until an owner turns it on. See [what triage needs before it can run](/concepts/cases#what-triage-needs-before-it-can-run).
- **Tessary explains and hands off.** It does not open the fix. A case reaches you through an alert rule and a notification destination you add, and [where a case reaches you](/concepts/cases#where-a-case-reaches-you) covers what that notification carries.
