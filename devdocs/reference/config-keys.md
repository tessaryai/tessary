# Config keys

All runtime config binds through `@ConfigurationProperties` classes discovered by
`@ConfigurationPropertiesScan`. Most live in `core`'s `config/` package; the handful that
belong to a feature carry that feature's module in the table below (`telemetry/` in `core`,
`featureflags/` in `tenancy`, …). Documented `@Value`
exceptions are listed at the bottom. Spring relaxed binding maps each dotted key to a
`SCREAMING_SNAKE_CASE` env var (e.g. `tessary.rca.batch-size` → `TESSARY_RCA_BATCH_SIZE`)
whether or not the key is declared in `application.yaml` — undeclared keys take
their default from the Java field.

Worker cadences (`heartbeat-ms` / `drain-interval-ms` / `schedule.heartbeat-ms`)
are bound directly by `@Scheduled(fixedDelayString=…)` on each worker, never on a
`*Properties` class.

Feature gating is a different axis — capabilities, their platform defaults and
LaunchDarkly targeting belong to the capability layer, not to this page.

## Prefix → class map

| Prefix | Class | Covers (key defaults) |
|---|---|---|
| `tessary.*` (core) | `config/TessaryProperties` | `jdbc-url`, `db-username`, `db-password`, `secret-key`, plus `site-domain`/`tls-mode`/`acme-email` (bound from the bare `SITE_DOMAIN`/`TLS_MODE`/`ACME_EMAIL` env vars below, not `TESSARY_*`) |
| `tessary.telemetry.*` | `telemetry/TelemetryProperties` | the `home.tessary.ai` heartbeat ping: `enabled` (true, opt-out). No token — the contract carries no third-party credential. See [`telemetry-contract.md`](./telemetry-contract.md) |
| `tessary.observer.*` | `config/ObserverProperties` | what the sandbox agent lanes lease and run on. The observer worker itself was removed, and this prefix is what outlived it: `lease-seconds` (1800) — read by `BehaviorTriageWorker`, whose jobs are agentic runs and so need a lease sized to `agentic.timeout-ms` rather than the classifier's 300s — plus `agentic.*` (`model` — a full Bedrock inference-profile id, `global.anthropic.claude-sonnet-5`; a bare foundation-model name 400s at the launcher — `timeout-ms` (1800000 / 30m), `max-turns` (52)) and `encoder.url`/`encoder.api-key` (the groundedness model server, `classifiers/groundedness/serve.py`) and `encoder.max-inflight` (2): concurrent `/classify` requests this backend keeps in flight across every sweep; the server queues past its own `--max-inflight` up to `--max-queue` and answers the rest with a 429, which the backend retries with backoff; `encoder.probe-interval-ms` (60000, the placeholder on `EncoderAvailability`'s `@Scheduled` probe, not a field here): how often `EncoderAvailability` asks the encoder's `/healthz`; up means a `200` whose `heads` lists `groundedness`, and the answer gates sweeping the encoder-backed classifier (`groundedness`) only: while it is down nothing is enqueued and a claimed sweep is handed back without spending an attempt, while the classifier, its findings and the org's switch stay as they are; served as the `encoder` health group. RCA and triage both read `agentic.model`. `max-turns` is threaded into the microVM agent's `maxSteps`, which forces a text-only reply at the cap rather than killing the run, so a capped run still lands a ruling. Two of the 52 go to that landing, so the user message states 50 and the agent works with 50. `timeout-ms` is a hard kill for a hung run, not a budget: it is never stated in the prompt, because a model cannot observe elapsed time, and it is sized slack around the turn cap so the turns run out first. There is no per-run spend cap: TRIAGE now offers the same models as RCA (see `data-model.md`'s `project_model_setting` entry), and the settings page's own price warning is the control on an expensive choice. **`observer` is a historical name and does not imply a surviving observer.** The namespace rename moved the prefix from `evals` to `tessary` and left the `observer` segment alone: renaming it too would break every deployment's env a second time for a word that still describes what the block configures |
| `tessary.classifier.*` | `config/ClassifierProperties` | async classifier-detection worker; `encoder-batch-size` (32) is the page an encoder-backed classifier (groundedness) sweeps in place of `batch-size`, so a backlog drains at the encoder's pace, one page's cursor at a time, and a failure re-scores one page (formerly `tessary.signal.*`/`SignalProperties` — persisted strings/tables stay `signal`): `batch-size` (200), `lease-seconds` (300), `max-attempts` (5), `dead-letter-cooldown-seconds` (1800), `triage-config-retry-seconds` (1800 — how long a triage job waits before re-checking a missing or unusable org credential). Cadence: `tessary.classifier.heartbeat-ms` (60000) in `ClassifierWorker`, `tessary.classifier.catalog-resync-ms` (60000) in `ClassifierCatalogWorker` (the built-in catalog reconcile — deliberately a SEPARATE cadence from the sweep heartbeat, and a separate project scope: the sweep enqueues for projects with observations, while the reconcile scans every active project, because which classifiers an org has answers to the capability flag layer and must not wait on that project having ingested a trace. Raising it only delays how long a freshly-flipped flag takes to reach an idle project; nothing downstream waits on a reconcile), and `tessary.classifier.behavior-triage-ms` (300000) in `BehaviorTriageWorker` (which leases from `tessary.observer.*`, not `lease-seconds` above — its jobs are agentic runs budgeted against `tessary.observer.agentic.timeout-ms`, so a 300s lease would let a long run be re-claimed and spawn a second microVM). Autonomous triage adds `triage-interval-ms` (900000 / 15m, the placeholder on `TriageAutoEscalator`'s `@Scheduled` tick, not a field here), `triage-min-trace-count` (2), `triage-breaker-failures` (3), `triage-breaker-cooldown-seconds` (300) and `triage-mcp-base-url` (blank) — the recurrence bar `TriageAutoEscalator` runs under, the launcher breaker that parks the drain when the sandbox launcher is refusing everyone, plus the door the ruling itself reads through. There is no per-tick or per-project ration: every eligible finding is scheduled and the queue holds the backlog. A tool-error finding closed by a `negative` ruling folds its judged window into that tool's reference and clears the arm it fired on, so a dismissed spell stops re-firing on evidence the ruling already dismissed — `positive` opens a case and touches no detector state. `triage-mcp-base-url` is the publicly reachable API origin the triage microVM calls back on, the same value `tessary.rca.agentic.mcp-base-url` carries; blank is a broken deployment rather than a degraded one, because the triage dossier is the detector's own numbers and nothing else — an agent with no MCP cannot open a single row of the population it is auditing, so the engine refuses to run and the job dead-letters. They apply only where `triage_automatic_enabled` is targeted on for the org; with the flag off the scheduler ticks and does nothing. A closed finding's cause firing again opens a fresh finding, triaged like any other -- there is no reopen path. |
| `tessary.groundedness.*` | `config/GroundednessProperties` | how this instance runs the groundedness model (its URL and key are `tessary.observer.encoder.*`): `classifier-mode` (`TESSARY_GROUNDEDNESS_CLASSIFIER_MODE`, `dev` or `production`, case-insensitive; unset or blank is `dev`, anything else fails startup) — `dev` sweeps whenever the model answers, `production` is a GPU instance that wakes on a schedule and stops itself when idle; `production-sleep-minutes` (30 — in production mode, how long after a sweep reaches the head of the stream groundedness is not enqueued again, so the instance can go idle and stop; the time is `caught_up_at` in the sweep job's `payload`); `production-missed-run-minutes` (120 — in production mode, how long without a caught-up sweep before the groundedness status reads `not_scoring`). The setup writes the mode into `.env` |
| `tessary.frustration.*` | `config/FrustrationProperties` | the Frustration classifier's decision-model calls (TypeSafe's Jev, direct or over OpenRouter, on the org's own key): `concurrency` (4 — turns of one page in flight at once; neither provider documents a rate limit), `timeout-ms` (20000 — per request; also binds `llm/decisions/JevDecisionClient`), `max-attempts` (3 — per turn, on a 429, a 5xx or a transport failure, with 1s/2s/4s back-off and `Retry-After` honoured), `page-retries` (3 — how many times a page on which more than half the sent turns failed on an unavailable provider is held and re-sent before it is skipped with one WARN), `credential-retry-seconds` (1800 — how long a paused classifier, `provider_rejected` or `no_provider`, waits before it checks the org's key again; a paused sweep sends nothing and advances past what it skips). The operating point is per-project data on the classifier's `config_json`, not a deployment key: `threshold` (0.40, a starting value) is the probability of `unhappy_with_assistant` above which a turn is flagged, and it is part of the assessment rows' `scorer_version`; the rate test that watches frustrated conversations per call site reads `arl_target` (10000 conversations between false alarms, a starting value), `min_decision_interval` (4, the floor on the derived threshold `h`, clamped to [2, 12], a starting value), `shift_multiple` (2.0), `shift_floor` (0.02) and `min_baseline_conversations` (200), parsed by `classifier/frustration/FrustrationConfig`; a change to any of them but the last resets each call site's learned rate |
| `tessary.ingest.spool.*` | `config/IngestSpoolProperties` | which `IngestSpool` buffers accepted batches: `mode` (`memory`, the default: in-process, bounded by `tessary.ingest.substrate.queue-max-bytes`, a restart loses what is queued; `kafka`: a Kafka-API broker, opt-in, accepted means persisted) and `max-lag-ms` (300000): the age of the oldest unprocessed batch past which the `/actuator/health/ingest` group (platform staff) and the top-level status are DOWN, `0` to disable, and the `kafka.*` block read only in that mode: `bootstrap-servers` (`redpanda:9092`, the bundled single-node Redpanda under `docker compose --profile kafka`), `topic` (`tessary.ingest`), `dead-letter-topic` (`tessary.ingest.dead-letter`, where a batch that exhausted its write retries is parked and committed so nothing is dropped and nothing blocks the partition), `group-id` (`tessary-ingest`), `partitions` (8, keyed by project so one project's batches stay ordered on one partition), `replication-factor` (1, all the bundled single-node Redpanda can satisfy; applied at topic creation, so it must be set before the first boot, and against a multi-broker cluster it is what makes an acknowledged batch survive losing a broker — above 1 the spool also sets `min.insync.replicas=2` so `acks=all` means two copies), `consumers` (4: drainer threads, one consumer each in the group, so throughput scales with cores while a project's partition is drained by one of them at a time; `memory` mode always runs one drainer), `max-message-bytes` (8 MiB, above which the edge answers OVERSIZE for the producer to split), `publish-timeout-ms` (10000, the wait for the broker's `acks=all` before a publish is a shed) |
| `tessary.ingest.substrate.*` | `config/SubstrateProperties` | async substrate write path: `queue-max-bytes` (**64 MiB**, the `memory` spool's ceiling — the hand-off queue's real ceiling, in payload bytes measured at admission and released after the drain. A full queue SHEDS the batch rather than blocking, and the ingest edge answers the producer with a retryable error — HTTP `503` + `Retry-After`, gRPC `UNAVAILABLE` — instead of a `200`, so a stock exporter re-sends into the idempotent write path. Bytes rather than batches because a batch holds its entries' payloads inline: in one bulk upload they ranged from 10 spans to 825 spans and 24.5 MB, so a batch count bounded nothing and a queue at half its slot capacity had already taken the heap. Every reference implementation that started with a count added a byte bound afterwards — Jaeger `queue-size-memory`, Datadog `forwarder_retry_queue_payloads_max_size`, the OTel Collector's `sending_queue.sizer: bytes`), `refuse-above-queue-fraction` (**0.8** — above this share of the byte budget the OTLP receiver refuses a push BEFORE decoding its body, answering `503` + `Retry-After`. The shed above is the last line and fires only after the batch is already in the heap it was meant to protect; this is the OTel Collector's `memorylimiterextension` / Phoenix `is_not_at_capacity` pattern. `0` disables it), `max-attempts` (3), `retry-backoff-ms` (250). v2 span resolvers: `resolver-batch-size` (500) rows per pass, and, read by `ingest/substrate/v2/PathResolver` (ancestry fixpoint) and `CorrelationBackfiller` themselves rather than bound here, `resolver-interval-ms` (1000, their `@Scheduled` placeholder) between passes and `resolvers-enabled` (true, their `@ConditionalOnProperty`) — an ops kill switch, not a rollout flag: both beans tick every second, and an operator must be able to stop a background job competing with ingest for connections. `resolver-statement-timeout-seconds` (30) bounds each resolver statement; a healthy pass takes milliseconds, and a cancelled one changes nothing and retries on the next tick. v2 trace rollups: `rollup-enabled` (true, the `@ConditionalOnProperty` on `TraceRollupWorker` and `TraceRollupReaper` — the same kind of kill switch; with it off the deadlines stay armed on the rows, so turning it back on drains the backlog), `rollup-interval-ms` (1000, `TraceRollupWorker`'s `@Scheduled` placeholder) and `rollup-claim-limit` (500) for `ingest/substrate/v2/TraceRollupWorker` (the §7.3 claim + §7.2 replacement recompute), and `rollup-reap-interval-ms` (60000, `TraceRollupReaper`'s `@Scheduled` placeholder), `rollup-reap-grace-seconds` (300), `rollup-stale-after-ms` (60000) for `TraceRollupReaper` (the §7.4 crash-fingerprint sweep, plus a log-only ERROR when the oldest due deadline falls further behind than `rollup-stale-after-ms` — because a rollup queue that stops draining is otherwise invisible: every trace surface keeps serving the last numbers written, with no gap and no error). The v1 → v2 backfill was a one-time cutover job; it and its config keys were deleted, along with `substrate_v2_id_map` and `substrate_v2_backfill_cursor`, once the sweep converged (the teardown release) — `SubstrateProperties` has no `backfill-*` field any more. Cadence: `tessary.ingest.substrate.report-ms` (60000) in `IngestThroughputReporter` — the `ingest.throughput` heartbeat the ingest dashboard is built from, which also carries the v2 span counters, the §7.6 span-lateness histogram and the rollup worker/reaper/queue-depth counters |
| `tessary.retention.*` | `config/RetentionProperties` | retention enforcement: `enabled` (true, the kill switch — `false` deletes nothing), `interval-ms` (3600000, the placeholder on `RetentionSweeper`'s `@Scheduled` sweep, not a field here), `batch-size` (5000), `max-batches-per-sweep` (20), and the platform default TTLs `trace-ttl-days` (90), `detection-ttl-days` (90 — the per-classifier detection tables, now defined in `0000-baseline.sql` after the migration-history squash; `embedding-ttl-days` was retired with the vector substrate it governed). A `retention_policy` row for a `(project, data_class)` overrides the matching TTL; `0` means keep forever. `media-grace-hours` (24) is not a TTL: unreferenced media is collected at any age, and this is only the window that keeps the collector off bytes a batch still in flight has stored but not yet referenced. The two bounds cap one statement and one project-class per pass, so a first sweep after a long unenforced period drains over passes instead of locking a table |
| `tessary.pricing.*` | `config/PricingProperties` | `enabled` (true, the kill switch — `false` neither imports the bundled book nor fetches one from home.tessary.ai, so every model prices as unpriced). `pricing/PriceBookImporter` imports the jar's `litellm-model-prices.json` into `price_book`/`model_price` on `ApplicationReadyEvent`; `pricing/PriceBookFetcher` imports a newer book from home on the telemetry heartbeat's 6-hour tick, only while `tessary.telemetry.enabled` is also true. ## Documented `@Value` exceptions

These `tessary.*` keys are `@Value`-injected directly and are **not** fields on any
`*Properties` class:

| Key | Location | Default |
|---|---|---|
| `tessary.classifier.encoder-dependency-report-ms` | `classifier/EncoderDependencyReporter` | `86400000` — how often the "can the encoder be turned off" line is emitted: projects with an enabled groundedness row whose org holds the capability, whether or not the model answers right now. Also fires once on boot |
| `tessary.media.cache.max-bytes` | `storage/CachingMediaStore` | `0` (falls back to the class's own `64 MiB` default) — the in-memory LRU read cache in front of `MediaStore`, sized for image-scale objects (a handful of images per grader call). Previously undocumented |

The agentic sandbox reaches mantle, Bedrock's second endpoint, through the launcher, not this backend. `MANTLE_PROJECT_ID`
(set from `TESSARY_MANTLE_PROJECT_ID` in both compose files) is still a deployment-wide launcher env
var — `MANTLE_REGION` is NOT: it was removed from the launcher's env along with
every other AWS credential var, and the region for a mantle run now comes per-request from the
org's own `credential.aws_region`. The launcher no longer signs mantle calls with any credential of
its own (dedicated IAM user or instance role): every `/rca` and `/triage` request carries the org's
own decrypted `ProviderCredential` (`aws_access_key`/`aws_secret_key`/`aws_region`), and an
`iam_role`-mode credential is explicitly refused before it ever reaches the launcher. The two
endpoints sit in two IAM namespaces and a grant on one gives nothing on the other: the standard
endpoint needs `bedrock:InvokeModel`, mantle needs `bedrock-mantle:CreateInference` scoped to the
Project's ARN.

## Env vars declared in `application.yaml`

Only these are declared with `${…}` defaults in `application.yaml`; every other
key relies on relaxed binding straight into its Properties class.

| Env var | Default | Notes |
|---|---|---|
| `TESSARY_JDBC_URL` / `TESSARY_DB_USERNAME` / `TESSARY_DB_PASSWORD` | (empty) | blank JDBC URL fails fast (`DataSourceConfig`) |
| `TESSARY_SECRET_KEY` | (empty) | base64 32-byte AES-GCM key (`SecretBox`). `docker-compose.yml` supplies a published placeholder so a self-host boots unconfigured; `PlaceholderSecretGuard` refuses the boot on it once `SITE_DOMAIN` is set |
| `SITE_DOMAIN` | (empty) | **The one key bound from a bare, un-prefixed name**, into `tessary.site-domain`. Deliberate: `docker-compose.yml`, `.env.example` and `frontend/caddy/render.sh` already share that spelling, and a second one would be a second thing to keep in sync. Empty means "localhost only", which is what keeps `PlaceholderSecretGuard` inert in every non-compose boot |
| `TLS_MODE` | `acme` | Bound bare into `tessary.tls-mode` for the same reason: how the frontend serves `SITE_DOMAIN` (`acme`, `owncert`, `upstream`). `PublicOriginGuard` rejects any other value, requires `ACME_EMAIL` in `acme` mode, requires `SITE_DOMAIN` to be a bare hostname, derives `tessary.auth.frontend-url` and `workos.redirect-uri` from it when they are still on a localhost default, and refuses the boot when either names a different host |
| `ACME_EMAIL` | (empty) | Bound bare into `tessary.acme-email`; the Let's Encrypt account address, read only by the guard above. No default anywhere: it is the operator's |
| `TESSARY_TELEMETRY_ENABLED` | `true` | `home.tessary.ai` heartbeat ping, opt-out. No frontend leg — see [`telemetry-contract.md`](./telemetry-contract.md) §4 |
| `TESSARY_PLATFORM_STAFF_EMAILS` | (empty) | comma-separated staff allowlist. **Empty ⇒ nobody**. In every build, gates `AuthFilter`'s bypass for the whole `/actuator/**` surface (heapdump, env, etc.) — listed identities get read access there with no org check. |
| `APP_LOG_LEVEL` | `INFO` | Boot `logging.level.ai.tessary` (+ logback `ai.tessary`) |

## Observability opt-in

Grafana Alloy, Grafana Cloud, Langfuse and Pyroscope are all **off by default** in the open build, so a self-hoster with no cloud observability account boots with zero export attempts. Two independent levers, both defaulting off — bringing the container up does not by itself turn export on, and vice versa.

| Knob | Where | Default | Notes |
|---|---|---|---|
| `COMPOSE_PROFILES=observability` | `docker-compose.dev.yml` | unset (Alloy not started) | The `alloy` service sits behind a Compose profile in the DEV file. Nothing else `depends_on` it. `task dev:profiling` adds the profile for you. ## Deploy-level worker switches vs product gating

Two deliberately distinct layers:

1. **Deploy-level `enabled` switches** stay `TESSARY_*` env config — they gate
   context-less worker loops and infrastructure:
   `tessary.predeploy.enabled`,
   `tessary.redaction.enabled`, `tessary.metering.storage-enabled`. (The classifier and
   RCA workers have **no** `enabled` field — they run unconditionally and gate
   per-project/org via capabilities.)
2. **Per-request product gating** is the capability axis — see
   the capability layer. The two are deliberately not merged: a
   deploy switch turns a process off for the whole deployment, a capability decides
   what one org has.

## LLM spend: reported, not capped

Every LLM lane (triage, RCA) runs on the org's own provider key and is deliberately
**uncapped**. Grading, which was the one lane that carried a
spend ceiling of its own, and the assistant were both removed entirely, so there is now no monetary cap anywhere in the open tree. What stands in
for a cap is attribution:

- Every LLM call books to `llm_call` with its lane, and every *sandbox* run also books the
  unit of work it was for (`subject_kind` / `subject_id`). For a Layer-2 ruling that is the `finding`
  it ruled on, which is what makes "what did one ruling cost" answerable. (`subject_kind` still reads
  `behavior_finding`, the name the table had when the column was written. It is a persisted string
  and is never renamed in place — rewriting it would orphan every spend row already booked under it.)

> **Renamed twice, and there is no alias either time.** The keys were `adjudication-*`
> (`TESSARY_CLASSIFIER_ADJUDICATION_AUTO_*`, `TESSARY_CLASSIFIER_BEHAVIOR_ADJUDICATION_MS`) before the
> model-lane cutover and `triage-auto-*` between it and the triage cutover; they are `triage-*` now, and
> the two budget keys changed meaning as well as spelling (a runaway bound, not a ration). A deployment
> that overrode any of them under an older name is silently back on the default, so re-set them before
> deploying. The persisted words moved with them this time: `finding.triage_*` replaced the
> `adjudication_*` columns and `job.kind='triage'` replaced `behavior_adjudication`, which
> discarded every stored ruling rather than reading one vocabulary as the other (now folded into
> `0000-baseline.sql` after the migration-history squash).

The lever that *does* bite is elsewhere and is deliberate: `triage_automatic_enabled` is off by
default, so rulings only happen when someone presses, and `TriageAutoEscalator` schedules every eligible finding
when it is on — the per-tick and per-project caps were removed, because the triage queue and its
two-microVM launcher pool are what bound the work, and a finding refused by a counter is one
nobody ever sees. What still gates it is `triage-min-trace-count`, and what stops a broken
launcher being retried into the ground is `TriageLauncherBreaker`. Per-org detail is readable in-app at
`GET /api/orgs/{orgSlug}/usage/llm/triages` (needs `BILLING_MANAGE`), which reports cost per
ruling alongside the whole-window total.
